## 2. 一次训练具体发生什么

```text
观测 obs（11 个数）
    → PPO 策略网络
    → 动作 action（1 个数）
    → 房间仿真推进 15 分钟
    → 新观测、奖励、是否到达回合结束、诊断信息
    → 重复采样，积累一批数据后更新策略和价值网络
```

策略网络不是预测整周温度，而是每个控制时刻决定当前空调功率。价值网络用于估计未来累计奖励，辅助 PPO 计算优势和更新策略。

需要区分三个计数：

- **step**：一次动作和状态推进，默认代表模拟时间 15 分钟。
- **episode**：一次从初始条件开始的完整轨迹，默认 7 天、672 步。
- **PPO update / epoch**：积累一批交互数据后进行更新；一次更新可以对同一批数据训练多个 epoch，并在各 epoch 内划分小批量。

`n_epochs=10` 是每批采样数据重复训练 10 轮，不是训练 10 个 episode。PPO 通常使用最近采集的数据更新，然后采集新一批；训练总步数与回合数是不同概念。

## 3. Gymnasium 环境是什么

Gymnasium 是强化学习环境接口库。这里的 **environment 是被控制的房间仿真器**，与安装 Python 包用的 `.venv` 虚拟环境无关。

它规定统一的交互接口，使同一个 PPO 实现可以接不同任务。它本身不会训练策略，也不会自动提供建筑物理方程；我们的 `HVAC2R2CEnv` 负责把队友的物理模型接到这套接口上。

| 接口 | 本项目的含义 |
| --- | --- |
| `observation_space` | 说明控制器会收到形状 `(11,)` 的 `float32` 数组及其合法范围 |
| `action_space` | 说明动作是形状 `(1,)`、取值 `[-1, 1]` 的连续数组 |
| `reset(seed=...)` | 开始新回合，抽取天气和初温，返回初始观测与信息 |
| `step(action)` | 执行动作，计算下一状态与奖励，返回五个值 |

可以先不使用 PPO，直接调用环境：

```python
import numpy as np
from hvac_env import HVAC2R2CEnv

env = HVAC2R2CEnv()
obs, initial_info = env.reset(seed=42, options={"scenario": "hot"})

for _ in range(env.config.episode_steps):
    action = np.array([-0.5], dtype=np.float32)  # 固定半功率制冷
    obs, reward, terminated, truncated, info = env.step(action)
    # info["indoor_temp_c"]：步后室温
    # info["energy_kwh_step"]：这 15 分钟的用电量
    if terminated or truncated:
        break

env.close()
```

这段循环只是固定动作的仿真，没有学习。接入 PPO 后，动作由策略产生，训练库负责采样和网络更新。

`step` 的五个返回值分别是：

- `obs`：下一时刻的观测；默认只有它作为策略输入。
- `reward`：标量训练信号，越大越好。
- `terminated`：任务本身的终止条件是否满足；当前模型始终为 `False`。
- `truncated`：是否达到外部时间上限；默认第 672 步为 `True`。
- `info`：额外的物理读数和诊断数据，用于统计、记录和绘图，默认不输入策略。

回合结束后调用方需要 `reset()`。使用 Stable-Baselines3 时，其向量环境封装会管理自动重置和时间截断；自己编写采样器时必须正确处理这些语义，不能把时间截断一律当作真实终止。

## 4. 队友的具体实现

### 4.1 热模型：两个动态温度状态

源码：[`thermal.py`](../RL_assignment/hvac_env/thermal.py)。

```text
室外温度 To ── 热阻 Reo ── 围护温度 Te、热容 Ce
                              │
                            热阻 Rie
                              │
                        室内温度 Ti、热容 Ci
                              ↑
                         空调功率 + 内部得热
```

对应方程是：

```text
Ci × dTi/dt = (Te - Ti) / Rie + Qhvac + Qg
Ce × dTe/dt = (To - Te) / Reo + (Ti - Te) / Rie
```

室温由围护换热、空调和内部得热共同决定；围护节点储热，使房间对室外变化有惯性。热阻越大越隔热，热容越大温度变化越慢。这里围护温度是集总模型的等效状态。

代码把方程写成线性状态空间形式，并在环境创建时用 SciPy 做一次零阶保持离散化，得到 `x_next = Ad @ x + Bd @ inputs`。每一步假设动作、外温与得热在该 15 分钟内保持恒定，因此推进很轻量。

### 4.2 空调动作与电量

源码：[`hvac.py`](../RL_assignment/hvac_env/hvac.py)。

- `u > 0` 供暖，`u < 0` 制冷，`u = 0` 关闭；默认两个方向最大热功率均为 1 kW。
- `u=-0.5` 表示净热功率为 −0.5 kW，不是目标温度设为 −0.5 °C。
- 默认供暖和制冷的 COP 均为 3：电功率 = 对应热功率的绝对值 / COP。
- 用电量 = 电功率 × 0.25 h。半功率制冷一步约用 `0.5 / 3 × 0.25 = 0.04167 kWh`。

这是理想设备的电耗估算，没有描述风机、湿度、启停和部分负载效率变化。

### 4.3 天气与观测

源码：[`weather.py`](../RL_assignment/hvac_env/weather.py)、[`env.py`](../RL_assignment/hvac_env/env.py)。

天气由日周期函数生成；每回合抽取冷、热、过渡场景之一，再抽取整段天气的温度偏移。内部得热包含基础、办公时段和日间三部分。

物理系统只有两个动态温度状态，但策略收到 **11 维观测**：室温、围护温度、外温、内部得热、舒适温度上下限、时刻的正弦和余弦、三维场景独热编码。

观测提供的是仿真器已知信息。真实建筑通常不能直接读到围护等效温度，因此报告应说明完整状态可观测的简化假设。当前也没有真实天气或建筑测量数据。

### 4.4 奖励与独立评价指标

源码：[`env.py`](../RL_assignment/hvac_env/env.py)、[`comfort.py`](../RL_assignment/hvac_env/comfort.py)。

以步后室温计算越界距离 `d = max(0, low - Ti, Ti - high)`。默认奖励按当前单位的数值计算：

```text
reward = -0.25 × d - 0.1 × energy_kwh_step
```

例如室温在舒适范围内且关闭空调，这一步奖励为 0；只要耗电或越界，奖励就为负，PPO 学习让总惩罚尽量小。权重 `1.0` 与 `0.1` 是项目设计选择，题目没有指定；比较 PPO 超参数时应固定它们。

报告需要分开显示：

| 指标 | 解释 |
| --- | --- |
| CVR，% | 温度越界的步末采样点比例，反映越界频率 |
| degree-hours，°C·h | 越界距离乘时间的累积，反映越界程度 |
| electricity，kWh | 每步用电量之和，不能再次乘步长 |
| 原始累计奖励 | 用于看学习进度，但不能代替上述物理指标 |

CVR 这里是步末采样近似，不代表连续时间下精确的越界时长。奖励也不等于电费；当前没有分时电价。

## 5. 后续具体怎么实现

以下为建议顺序，各阶段完成后保留可复现的配置和结果。

### A. 本机复验环境

创建 Python 3.12 独立环境，安装队友包及验证依赖；重跑既有测试、Gymnasium `check_env` 和固定动作脚本。然后安装 Stable-Baselines3，在 CPU 上运行。

### B. 训练一个默认 PPO

先使用小型全连接网络，跑通采样、训练、保存、重新加载和评估。以下仅为接入示意，尚非项目训练入口：

```python
from stable_baselines3 import PPO
from hvac_env import HVAC2R2CEnv

env = HVAC2R2CEnv()
model = PPO(
    "MlpPolicy", env,
    clip_range=0.2, gae_lambda=0.95, n_epochs=10,
    device="cpu", seed=0, verbose=1,
)
model.learn(total_timesteps=100_000)  # 短跑起点，不保证已收敛
model.save("checkpoints/ppo_default")
env.close()
```

正式训练建议对观测做归一化。若使用 `VecNormalize`，需要保存统计量，评估时复用并冻结；最终汇报原始奖励和物理指标。先完成短跑并测训练速度，再决定完整预算。

训练阶段需要补：统一的参数入口、种子控制、配置及依赖版本记录、日志、模型保存，以及归一化统计的保存与加载。

### C. 统一评估与规则控制器

建立固定测试场景表：记录场景、天气偏移、初始室温和围护温度。所有模型在相同测试条件下评估，测试条件与训练抽样分开；评估时不更新网络。

建议加入简单恒温器作为对照，例如低于下限供暖、高于上限制冷、范围内关闭。该对照不是题目明文要求，但能帮助判断学习策略是否有实际价值。关闭空调、随机动作可用作调试参照。

三类天气分别统计指标，再按明确且固定的权重汇总；画出典型轨迹的室温、舒适区间、外温、动作和累计电量。不要只挑表现最好的一条轨迹。

### D. 三个超参数的消融

| 参数 | 作用 | 建议候选值 |
| --- | --- | --- |
| `clip_range` | PPO 的裁剪目标抑制过大的策略变化；不是硬性保证所有策略概率比都在范围内 | 0.1、0.2、0.3 |
| `gae_lambda` | 改变 GAE 对不同时间跨度 TD 残差的加权，影响优势估计的偏差与方差 | 0.90、0.95、0.99 |
| `n_epochs` | 同一批采样数据重复训练的次数；增加可能提高数据利用率，也可能使更新过强 | 5、10、20 |

以 `(0.2, 0.95, 10)` 为共同基准，每次只改变一个参数。基准只需跑一次，因此是 **1 + 2 + 2 + 2 = 7 个不同配置**；使用 3 个训练种子则共 21 次训练。这能观察单个参数的影响，但不能回答参数间所有交互作用。

保持环境、奖励、网络、归一化方法、其余 PPO 参数、训练采样步数和评估条件一致。注意 `n_steps × n_envs` 决定一批采样量；更改它们会改变更新节奏，不能在消融中随意变动。

先短跑筛查问题，再依据曲线决定是否统一增加预算。正式比较以相同环境交互步数为主，同时报告实际训练时间，因为不同 `n_epochs` 的计算成本不同。

### E. 结果分析与交付

训练稳定性至少展示原始评估回报随采样步数的变化，以及不同训练种子的均值和标准差；可结合 `approx_kl`、`clip_fraction`、熵、价值误差和异常回落解释更新情况。单次运行的平滑曲线或单个 loss 不能充分证明稳定。

最终整理各配置的 CVR、degree-hours、kWh 和运行时间，讨论差异是否跨种子一致、是否存在舒适度与能耗权衡。结果不必证明某组参数总是最好；应如实分析有效差异和证据不足的地方。

报告围绕问题与文献、模型与 PPO 方法、消融设置、结果、限制与结论展开。程序要提供安装说明、训练/评估/绘图入口、配置和种子，使报告图表能对应到真实运行结果。展示材料需控制在 12 分钟内。
